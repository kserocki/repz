# ADR-0028: Number keypad and display numbers

- **Status:** Accepted (2026-11-06, REP-35)

## Context
C11 needs a reusable number keypad sheet (weight/reps/RPE) for at least two features — the live workout now, the template editor later (board 08) — so it can't live in a `feature:*:impl` (Konsist A2 would block the second feature). `core:designsystem` is documented as domain-free (ARCHITECTURE §3: no `core:domain` edge), but the keypad's own editing rules (what "82." plus a digit becomes, whether a keystroke is within range) are exactly the kind of pure logic that belongs next to the component it drives, not duplicated per feature, and need to run inside `core:designsystem`'s own debug catalog so the component is testable before any feature wires it up. Those two constraints — domain-free, yet reusable pure logic — are resolved by splitting the keypad itself from the one piece that has to know domain types: unit conversion.

## Decision
- **`core:designsystem` stays domain-free; a new display-number type carries the split.** `FixedDecimal` (`core:designsystem`'s `format` package) is a `@JvmInline value class` over `Long` hundredths — non-negative, exact, two fixed fraction digits, no float drift — and is the only numeric type the keypad ever touches: `NumberKeypadSheet`, `NumberKeypadRequest`, `KeypadField`, `KeypadRules` and `KeypadQuickValues` all work on `FixedDecimal`, never on `Weight`, `Rpe` or grams. This is what keeps the whole component testable from `core:designsystem`'s own catalog pages (`keypad-weight`/`-reps`/`-rpe`/`-motion`), which can't see `core:domain`.
- **`core:ui` gets a new dependency, `core:domain`** (ARCHITECTURE §3 diagram: `UI --> DOMAIN`), and owns the one adapter that knows domain types: `com.repz.app.core.ui.keypad.SetValueKeypad` (`SetValueKeypadRequest`/`SetValueEdit`/`SetValueField`/`SetValues`) maps `Weight`/`Rpe`/`UnitSystem`/`WeightStep` to and from `FixedDecimal` and renders `NumberKeypadSheet`; `com.repz.app.core.ui.format.WeightFormat` (`toDisplay`/`fromDisplay`/`maxSetWeight`) plus the `@Composable formatSetWeight`/`formatSetWeightWithUnit`/`weightUnitLabel` functions are the one locale-aware set-weight formatter every screen that shows a weight uses. `core:ui` is now the only module besides `feature:*:impl` that depends on `core:domain`, and it still follows Konsist T1 (no hard-coded dp/sp/colour/spring outside `core:designsystem`): everything visual stays in the sheet, `core:ui` only converts numbers and resolves strings.
- **The one conversion point stays ADR-0022's:** `WeightFormat.fromDisplay` is `Weight.fromUnit(amount.hundredths / 100.0, unit)`, called exactly once per accepted edit. `toDisplay` goes the other way in exact integer maths with half-up rounding — kg is `(grams + 5) / 10` (a gram is exactly a tenth of a display hundredth); lb scales the numerator by `10^7` before dividing by the exact grams-per-pound ratio (`45 359 237`), since a pound has no exact decimal gram equivalent. `maxSetWeight(unit)` is `toDisplay(ValidationLimits.SET_WEIGHT_MAX, unit)`, verified to be the largest display value whose `fromDisplay` still clears that limit.
- **The locale decimal separator is an `expect`/`actual`,** `internal expect fun platformNumberSymbols(): RepzNumberSymbols` in `core:designsystem`'s `format` package: Android reads `DecimalFormatSymbols.getInstance(Locale.getDefault()).decimalSeparator`; iOS reads `NSLocale.currentLocale.decimalSeparator` (first character, falling back to `'.'`). `rememberRepzNumberSymbols()` re-reads it when the composition's locale changes. Set weights (max 2204.62) show **no grouping separator** — `FixedDecimal.format` never groups; a future volume display that needs one (with the U+00A0 thin space) extends `RepzNumberSymbols` rather than changing this type's contract. iOS's `NSLocale.currentLocale` follows the region format, not the per-app language, so Spotter's manual PL check sets both.
- **The edit buffer lives in the sheet, keyed by target, not in the caller's state.** `KeypadBuffer(text, isUntouched)` is `rememberSaveable(request.targetKey, request.field.mode)`, so it survives recomposition and process death but resets whenever the caller retargets it (a new set, or switching fields within the same set — `SetValueKeypadMapping` appends the field to the key for exactly this reason). The caller's own state holds only domain values; every accepted change calls `onValueChange` live (no explicit confirm/cancel — hiding the sheet keeps the last value).
- **Editing rules** (`KeypadRules`, pure, no Compose): an untouched buffer (just opened, retargeted, or right after ±/a chip/"Same as last"/an RPE key) is replaced by the first digit or separator; a touched buffer appends. At most `fractionDigits` fraction digits; a keystroke that would exceed the field's `max` is refused with the buffer unchanged. Two single-key-press behaviours were under-specified by the implementation plan and were decided as follows while building `KeypadRules`:
  - **A digit, separator or backspace press in RPE mode is *ignored*, not *refused*.** RPE is never typed (its only input is the 9 `Rpe.ALL` choices or ±), and the sheet hides those three keys in RPE mode, so this path is reachable only from a hardware keyboard. It returns `isRejected = false` (no `reject()` haptic) rather than `true`, because nothing about the input was wrong for a value that simply isn't editable that way — it's a no-op, not a mistake. Every other buffer-unchanged outcome (a second decimal separator, the fraction-digit limit, over-`max`, ± already at its limit) does return `isRejected = true` and does haptic-reject.
  - **`stepDecrease` refuses rather than clamps to `min`.** The plan specified `stepIncrease` explicitly ("clamped to max, rejected only when already at max") but described `stepDecrease` only as "refused below min", without the word "clamped". Read literally, decrease refuses the whole step (buffer unchanged, `reject()`) whenever `current − step < min`, even from a value strictly above `min` that's closer than one full step away — it does not snap down to `min` the way increase snaps up to `max`. The two directions are therefore asymmetric by design, not an oversight.
- **Quick values never invent plate maths.** `KeypadQuickValues.weightSuggestions` reads the plan's "rounded to available plates" as "rounded to a multiple of the current step" (no plate-inventory feature exists): base ± 1/± 2 steps, each rounded half-up to a step multiple, filtered for duplicates/the base/out-of-range, ascending. `repsSuggestions` is the fixed list 5, 6, 8, 10, 12. See DESIGN_SYSTEM §13 for the one place this algorithm's tested output doesn't match either board's sample numbers (the boards disagree with each other too; the code wins).

## Consequences
- A future feature that needs the keypad (the template editor, board 08) reuses `NumberKeypadSheet` and `SetValueKeypad` as-is; it never needs its own number-formatting or editing-rule code, and never imports `FixedDecimal`/`KeypadRules` directly (§8.1 of the REP-35 plan is the frozen contract).
- `core:ui` crossing into `core:domain` is a one-time, documented exception to "`core:ui` is domain-free" (which was never actually a written rule — ARCHITECTURE only drew `core:designsystem` as domain-free); any later `core:ui` addition that also needs domain types reuses this same edge instead of asking for a new one.
- Changing the weight-step default or adding a new step size is a `core:domain` change only (`WeightStep`, ADR-0026 amendment); it never touches `core:designsystem`.
- The RPE-ignored-vs-refused and decrease-clamp-vs-refuse behaviours are covered by `KeypadRulesTest` and are therefore a deliberate contract, not accidental; changing either is a test change plus a note here, not a silent behaviour drift.
