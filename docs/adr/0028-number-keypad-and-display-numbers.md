# ADR-0028: Number keypad and display numbers

- **Status:** Accepted (2026-11-06, REP-35)

## Context
C11 needs a reusable number keypad sheet (weight/reps/RPE) for at least two features — the live workout now, the template editor later (board 08) — so it can't live in a `feature:*:impl` (Konsist A2 would block the second feature). `core:designsystem` is documented as domain-free (ARCHITECTURE §3: no `core:domain` edge), but the keypad's own editing rules (what "82." plus a digit becomes, whether a keystroke is within range) are exactly the kind of pure logic that belongs next to the component it drives, not duplicated per feature, and need to run inside `core:designsystem`'s own debug catalog so the component is testable before any feature wires it up. Those two constraints — domain-free, yet reusable pure logic — are resolved by splitting the keypad itself from the one piece that has to know domain types: unit conversion.

## Decision
- **`core:designsystem` stays domain-free; a new display-number type carries the split.** `FixedDecimal` (`core:designsystem`'s `format` package) is a `@JvmInline value class` over `Long` hundredths — non-negative, exact, two fixed fraction digits, no float drift — and is the only numeric type the keypad ever touches: `NumberKeypadSheet`, `NumberKeypadRequest`, `KeypadField`, `KeypadRules` and `KeypadQuickValues` all work on `FixedDecimal`, never on `Weight`, `Rpe` or grams. This is what keeps the whole component testable from `core:designsystem`'s own catalog pages (`keypad-weight`/`-reps`/`-rpe`/`-motion`), which can't see `core:domain`.
- **`core:ui` gets a new dependency, `core:domain`** (ARCHITECTURE §3 diagram: `UI --> DOMAIN`), and owns the one adapter that knows domain types: `com.repz.app.core.ui.keypad.SetValueKeypad` (`SetValueKeypadRequest`/`SetValueEdit`/`SetValueField`/`SetValues`) maps `Weight`/`Rpe`/`UnitSystem`/`WeightStep` to and from `FixedDecimal` and renders `NumberKeypadSheet`; `com.repz.app.core.ui.format.WeightFormat` (`toDisplay`/`fromDisplay`/`maxSetWeight`) plus the `@Composable formatSetWeight`/`formatSetWeightWithUnit`/`weightUnitLabel` functions are the one locale-aware set-weight formatter every screen that shows a weight uses. `core:ui` is now the only module besides `feature:*:impl` that depends on `core:domain`, and it still follows Konsist T1 (no hard-coded dp/sp/colour/spring outside `core:designsystem`): everything visual stays in the sheet, `core:ui` only converts numbers and resolves strings.
- **The one conversion point stays ADR-0022's:** `WeightFormat.fromDisplay` is `Weight.fromUnit(amount.hundredths / 100.0, unit)`, called exactly once per accepted edit. `toDisplay` goes the other way in exact integer maths with half-up rounding — kg is `(grams + 5) / 10` (a gram is exactly a tenth of a display hundredth); lb scales the numerator by `10^7` before dividing by the exact grams-per-pound ratio (`45 359 237`), since a pound has no exact decimal gram equivalent. `maxSetWeight(unit)` is `toDisplay(ValidationLimits.SET_WEIGHT_MAX, unit)`, verified to be the largest display value whose `fromDisplay` still clears that limit.
- **The locale decimal separator is an `expect`/`actual`,** `internal expect fun platformNumberSymbols(): RepzNumberSymbols` in `core:designsystem`'s `format` package: Android reads `DecimalFormatSymbols.getInstance(Locale.getDefault()).decimalSeparator`; iOS reads `NSLocale.currentLocale.decimalSeparator` (first character, falling back to `'.'`). `rememberRepzNumberSymbols()` re-reads it when the composition's locale changes. Set weights (max 2204.62) show **no grouping separator** — `FixedDecimal.format` never groups; a future volume display that needs one (with the U+00A0 thin space) extends `RepzNumberSymbols` rather than changing this type's contract. iOS's `NSLocale.currentLocale` follows the region format, not the per-app language, so Spotter's manual PL check sets both.
- **The edit buffer lives in the sheet, keyed by target, not in the caller's state.** `KeypadBuffer(text, isUntouched)` is `rememberSaveable(request.targetKey, request.field.mode)`, so it survives recomposition and process death but resets whenever the caller retargets it (a new set, or switching fields within the same set — `SetValueKeypadMapping` appends the field to the key for exactly this reason). The caller's own state holds only domain values; every accepted change calls `onValueChange` live (no explicit confirm/cancel — hiding the sheet keeps the last value).
- **Editing rules** (`KeypadRules`, pure, no Compose): an untouched buffer (just opened, retargeted, or right after ±/a chip/"Same as last"/an RPE key) is replaced by the first digit or separator; a touched buffer appends. At most `fractionDigits` fraction digits; a keystroke that would exceed the field's `max` is refused with the buffer unchanged. Two single-key-press behaviours were under-specified and were decided as follows while building `KeypadRules`:
  - **A digit, separator or backspace press in RPE mode is *ignored*, not *refused*.** RPE is never typed (its only input is the 9 `Rpe.ALL` choices or ±), and the sheet hides those three keys in RPE mode, so this path is reachable only from a hardware keyboard. It returns `isRejected = false` (no `reject()` haptic) rather than `true`, because nothing about the input was wrong for a value that simply isn't editable that way — it's a no-op, not a mistake. Every other buffer-unchanged outcome (a second decimal separator, the fraction-digit limit, over-`max`, ± already at its limit) does return `isRejected = true` and does haptic-reject.
  - **`stepDecrease` refuses rather than clamps to `min`.** `stepIncrease` was specified explicitly ("clamped to max, rejected only when already at max") while `stepDecrease` was specified only as "refused below min", without the word "clamped". Read literally, decrease refuses the whole step (buffer unchanged, `reject()`) whenever `current − step < min`, even from a value strictly above `min` that's closer than one full step away — it does not snap down to `min` the way increase snaps up to `max`. The two directions are therefore asymmetric by design, not an oversight.
- **Quick values never invent plate maths.** `KeypadQuickValues.weightSuggestions` reads the original "rounded to available plates" guidance as "rounded to a multiple of the current step" (no plate-inventory feature exists): base ± 1/± 2 steps, each rounded half-up to a step multiple, filtered for duplicates/the base/out-of-range, ascending. `repsSuggestions` is the fixed list 5, 6, 8, 10, 12. See DESIGN_SYSTEM §13 for the one place this algorithm's tested output doesn't match either board's sample numbers (the boards disagree with each other too; the code wins).

## Consequences
- A future feature that needs the keypad (the template editor, board 08) reuses `NumberKeypadSheet` and `SetValueKeypad` as-is; it never needs its own number-formatting or editing-rule code, and never imports `FixedDecimal`/`KeypadRules` directly — `SetValueKeypad`'s §8.1 contract is frozen.
- `core:ui` crossing into `core:domain` is a one-time, documented exception to "`core:ui` is domain-free" (which was never actually a written rule — ARCHITECTURE only drew `core:designsystem` as domain-free); any later `core:ui` addition that also needs domain types reuses this same edge instead of asking for a new one.
- Changing the weight-step default or adding a new step size is a `core:domain` change only (`WeightStep`, ADR-0026 amendment); it never touches `core:designsystem`.
- The RPE-ignored-vs-refused and decrease-clamp-vs-refuse behaviours are covered by `KeypadRulesTest` and are therefore a deliberate contract, not accidental; changing either is a test change plus a note here, not a silent behaviour drift.

## Amendment (2026-11-07, REP-35 review-1): `KeypadEdit.rejection` replaces `isRejected`

Coach's round-1 review found the sheet showing the "Weight must be 0–1000 kg" limit message for refusals that were never actually out of range: a third fraction digit, a second decimal separator, Backspace on an empty buffer, a reps separator reachable only from a hardware keyboard. `KeypadEdit.isRejected: Boolean` collapsed two different reasons into one flag, so `NumberKeypadSheetStateless` couldn't tell them apart.

**Decision:** `KeypadEdit` now carries `rejection: KeypadRejection?` (`null` = accepted) instead of `isRejected: Boolean`, where `KeypadRejection` is `OutOfRange` (a keystroke or ± that would leave `min..max`) or `Format` (malformed input that was never evaluated against the range). Both still fire `reject()` and stop the ± long-press repeat; only `OutOfRange` replaces the context line with the limit message. The RPE-ignored case above is unchanged (`rejection = null`, not a rejection at all). `KeypadEdit` is internal to `core:designsystem`'s `keypad` package and isn't part of §8, so this is not a breaking change for any feature wiring the keypad.

## Amendment (2026-11-07, REP-35 review-1 round-2): grid row collapse, stale buffer, hero font-scale cap

QA's round-2 pass found two regressions introduced by the review-1 fixes themselves, plus a user decision on the hero's accessibility ceiling.

**Bug A — a grid row collapsed to zero size.** `KeypadGrid.kt`'s row-3/4 block (and both of RPE's two-row blocks) put two `Row`s in a plain `Column` next to a `fillMaxHeight()` rail key, inside an outer `Row(Modifier.height(IntrinsicSize.Min))`. Without their own `weight`, the two inner rows each independently measured against the whole block's height budget instead of splitting it, so one row claimed it all and the other was laid out at 0×0 — invisible and untappable (confirmed by `uiautomator`: `bounds=0,0,0,0` on the decimal/0/hide row and RPE's middle choice row). **Decision:** a new `TwoRowKeyColumn` wraps the pair in a `Column(Modifier.weight(1f).height(IntrinsicSize.Min))` whose two `Row`s each carry `Modifier.weight(1f)`, splitting the resolved intrinsic height evenly and deterministically. Used for all three two-row-plus-rail-key blocks (digit grid rows 3–4, RPE's Clear span, RPE's Next span).

**Bug B — touch input kept mutating a stale buffer after a mode/unit switch.** `NumberKeypadSheetStateful` keyed the edit buffer's own `rememberSaveable(targetKey, mode)`, recreating a brand-new `MutableState` object on every retarget. The display (fed `buffer` as a plain parameter every recomposition) always showed the new target correctly, but a button whose click handler a skipped recomposition hadn't refreshed yet could still be bound to the discarded, orphaned state object — so a digit/±/chip tap right after a mode or unit switch silently mutated the *old* buffer (observed: typing "1" after a kg→lb toggle logged "11", concatenating onto the pre-toggle buffer, while the hero stayed frozen on the new target's value). Hardware keys, the Step chip, mode/next/dismiss were unaffected, since none of them read through this per-target-recreated object. **Decision:** the buffer and its dispatch function now keep one stable identity for the whole lifetime of `NumberKeypadSheetStateful`. Retargeting resets the buffer's *value* (compared via a new `retargetKeyOf(request)` string key) instead of recreating its state object, and `dispatch` is `remember`ed once, reading `request`/`onValueChange` through `rememberUpdatedState` — so however old a captured `dispatch` reference is, it always reads the one true buffer and the latest callbacks. No stale closure is possible any more, regardless of what any downstream composable skips.

**Hero font-scale cap (user decision).** The hero's `TextAutoSize` range (22–52 sp) still scaled with the real system font scale, with no ceiling; iOS AX5 (≈3.1×) is well past the 2.0× the 52/56 sizing was designed and verified against. **Decision:** the hero `Text` alone is wrapped in `CompositionLocalProvider(LocalDensity provides …)` with a `Density` whose `fontScale` is `min(ambient fontScale, 2.0)` — every other text in the sheet (mode labels, chips, grid, context line) keeps following the real system font scale. See DESIGN_SYSTEM §13.
