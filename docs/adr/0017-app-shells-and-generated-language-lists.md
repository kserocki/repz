# ADR-0017: App shells: Xcode project, static framework, generated language lists and icons

- **Status:** Accepted (2026-10-29)

## Context
REP-11 ships the first launchable app on both platforms: the Android app module, the iOS SwiftUI host and framework export, and Koin start. Several infrastructure choices had no precedent yet: how the iOS Xcode project is created and kept in the repo, how `app:shared` reaches iOS, where the supported-language list and the app name come from, how launcher/splash assets are produced from the brand exports, and which devices/orientations v1 targets.

## Decision
- **iOS project:** a hand-made, committed `mobile/iosApp/iosApp.xcodeproj` (Xcode 27.1, folder-synchronized groups / `PBXFileSystemSynchronizedRootGroup`), no XcodeGen/Tuist. Build settings live in a committed `Configuration/Config.xcconfig`; a git-ignored `Local.xcconfig` holds a personal `DEVELOPMENT_TEAM`. A single app target does not justify an extra generator tool, and `AGENTS.md` already promises `open mobile/iosApp/iosApp.xcodeproj`.
- **Framework export:** `app:shared` exports a **static** framework `RepzShared` for `iosArm64`/`iosSimulatorArm64`, linked by the Xcode run-script phase `embedAndSignAppleFrameworkForXcode` — the Kotlin-recommended direct Gradle↔Xcode integration, no CocoaPods/SPM. Static avoids a dyld cost at launch.
- **Generated language lists:** the canonical set of supported app languages is the `values-*` folders of `mobile/app/shared/src/commonMain/composeResources/` (which hold `app_name`). A Gradle task reads them into Android `res/values-*/strings.xml`, picked up by AGP's `generateLocaleConfig`; another Gradle task generates, per locale, a `<tag>.lproj/InfoPlist.strings` plus an index file, applied to the built app's `CFBundleLocalizations` by an Xcode build-time script. Adding a language means adding one `values-<lang>` folder — never editing a hand-written list on either platform.
- **Generated icons:** Android launcher and splash VectorDrawables are generated by a deterministic script (`brand/logo/src/android_vectors.py`) from the brand SVG exports, never hand-converted. iOS app-icon and launch-screen images are copied as-is from the brand PNG/SVG exports by `mobile/iosApp/scripts/sync-brand-assets.sh`. Neither generated output is ever hand-edited; both scripts are idempotent (re-running either leaves `git status` clean).
- **Devices and orientation** (user decision, 2026-10-29 — overrides the "no lock" recommendation): iOS targets **iPhone only** (`TARGETED_DEVICE_FAMILY = 1`). Both platforms are **locked to portrait**: `android:screenOrientation="portrait"` on `MainActivity`, `UISupportedInterfaceOrientations = [UIInterfaceOrientationPortrait]` in `Info.plist`.
- **Splash:** the brand symbol is **144 dp/pt** wide on both platforms. On Android, the SplashScreen API lays `windowSplashScreenAnimatedIcon` out in its **288 dp "no icon background" box**. A same-colour `windowSplashScreenIconBackgroundColor` doesn't switch it to the 240 dp box: measured, the 108-grid geometry at 60% occupancy renders at 172.8 dp, not 144 dp. `brand/logo/src/android_vectors.py` compensates with a splash-only `SPLASH_SYMBOL_SCALE` (5/6, centred on the viewport) that shrinks the drawn geometry to 50% occupancy, rendering at 144 dp in that 288 dp box. iOS follows system appearance like Android (paper/deep by day, ink/cyan by night) instead of a fixed dark screen.

## Amendment (2026-11-05, REP-21)
The splash icon is now **bar-only**, not the complete symbol (user decision, splash continuity): `logo/src/android_vectors.py` emits `splash_bar.xml` from `symbol.svg`'s `bar` path alone, reusing the same `SPLASH_SYMBOL_SCALE`/288 dp-box transform this ADR already fixed — only what's drawn inside that frame changed, not its scale or position. iOS's `LaunchBar` image set (`logo/color/symbol-bar-{deep,cyan}.svg`) replaces `LaunchSymbol` in `LaunchScreen.storyboard`, at the same unchanged 155.68 × 77.84 pt frame. Both still render the documented 144 dp/pt artwork width. `brand/LOGO.md` §5 and the ADR-0025 amendment cover why (the app's launch layer draws the identical bar from its first Compose frame, so the hand-off is invisible, and MOT-01 then loads the plates onto it).

`logo/src/compose_logo.py` (stdlib only, same shape as `android_vectors.py`) joins the generated-asset family this ADR already makes CI-verified: `mobile.yml`'s `brand-assets` job runs it alongside the other two generators and fails the build on drift. It emits `core:designsystem`'s `RepzLogoGeometry.kt` and `logo_wordmark.xml` from the same brand SVG sources (`symbol.svg`, `lockup-stacked.svg`, `master/wordmark.svg`), so the Compose symbol's geometry is never hand-typed.

Measured hand-off tolerance: per-frame pixel measurement (not eyeballed) of cold-start recordings shows the native splash frame and the first Compose frame's bar within 1 px of each other on both platforms — tight enough that the native-to-Compose transition reads as one continuous frame.

## Consequences
No iOS project generator or extra dependency manager enters the toolchain. Supporting a new UI language only touches Compose resource folders under `app:shared`; both platforms' manifests/plists stay generated, never hand-maintained, so they cannot drift from that single source — checked by a disposable `values-<lang>` folder making the language appear on both platforms with no other change (REP-11 acceptance criteria). Regenerating icons from the brand exports is scripted; idempotency is checked in CI by the `brand-assets` job of `mobile.yml` (re-run the scripts, `git status` must be clean; ADR-0018). The portrait lock is revisited only if a later screen (REP-50/REP-51) needs rotation; until then every screen can assume a fixed portrait layout, and iPhone-only means no iPad-specific layout work is needed yet. Android lint flags the lock (`LockedOrientationActivity`, `DiscouragedApi`: Android 16+ ignores fixed orientations on screens ≥ 600 dp). By user decision these two checks are suppressed only on the `MainActivity` `<activity>` element via `tools:ignore`, not globally and not in a baseline.
- Xcode 27.1 rejects declaring the built Info.plist as an output of the localization run-script, because the Info.plist step already produces it. The phase lists it as an input only. The static framework's bundled ICU object reports iOS-simulator 18.5 while the app targets 18.0; this is harmless on 18.5+ and noted in case of trouble on 18.0–18.4.
