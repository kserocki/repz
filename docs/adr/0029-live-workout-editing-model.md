# ADR-0029: Live workout editing model

- **Status:** Accepted (2026-11-06, REP-34). Amended 2026-11-13 (REP-34): added the locked Start/Finish/Discard wrappers, corrected the Consequences bullet to cover every write (not only Edit/AddExercise), recorded that REP-38 calls `FinishLiveWorkoutUseCase`, and recorded the draft-persistence rules (debounce, flush points, character caps); no further code change. Amended 2026-11-24 (REP-37): the exercise picker (C13) adds multi-exercise add (one write for the whole pick order) and Replace (swap a card's exercise in place); see "Multi-add and Replace" below.

## Context
The live workout (C10) is the first screen that edits an aggregate the user is actively building, offline, one field at a time, while it is still a local-only draft (ADR-0023: `finished_at IS NULL`, never validated, never synced). REP-34 needed a model for: how an edit reaches Room without losing a concurrent one, what state is cosmetic enough to skip Room entirely, how a newly added exercise or set gets its starting values, how "Finish" turns a draft into a real history row, and which screens the app shows full-screen with no nav bar.

## Decision

### Pure edit functions, one write path
Every edit — rename, add/remove/replace/reorder an exercise, add/remove/update a set, exercise notes — is a pure, total function on `Workout` in `core:domain`, split by concern into `ActiveWorkoutEdits.kt` (`renamed`, `withExercisesAppended`, `withExerciseReplaced`, `withExerciseInserted`/`withoutExercise`, `withExerciseMoved`, `withExerciseNotes`) and `ActiveWorkoutSetEdits.kt` (`withSetAppended`/`withSetInserted`/`withoutSet`, `withSetUpdated`, plus `findSet` (owning exercise + index, for undo) and the `completedSetCount` property) — two files rather than one so neither crosses Detekt's per-file function-count limit. An edit against an id the workout doesn't have is a no-op, not a failure: by the time a UI edit reaches here, the ViewModel's own copy of the workout can only be a step behind the latest Room emission, never pointing at something that was never there. Index arguments are clamped into range instead of throwing, so a stale index from an undo still lands somewhere sane.

`feature:workout:impl`'s `EditActiveWorkoutUseCase(edit: (Workout) -> Workout): Boolean` is the **one** write path every feature-local use case and every `LiveWorkoutViewModel` intent handler goes through: read the latest active workout, apply `edit`, save the whole aggregate back (`saveActiveWorkout`, ADR-0023's replace-all-children write), under one app-scoped `ActiveWorkoutWriteLock` (`@Single`, wraps a `Mutex`). The lock exists because two edits racing a read-modify-write of the same aggregate would otherwise let the second write silently discard the first's change; serializing the whole read-modify-write under one mutex is simpler and safer than field-level merging. `AddExercisesToActiveWorkoutUseCase` and `ReplaceExerciseInActiveWorkoutUseCase` take the same lock directly (they need to read-modify-write too, from a last-performance lookup to the appended or replacement exercise), and so do `StartEmptyLiveWorkoutUseCase`, `StartLiveWorkoutFromTemplateUseCase`, `FinishLiveWorkoutUseCase` and `DiscardActiveWorkoutUseCase` — feature-local wrappers around `core:domain`'s `StartEmptyWorkoutUseCase`/`StartWorkoutFromTemplateUseCase`/`FinishActiveWorkoutUseCase` and `WorkoutRepository`'s discard, so a queued edit can never read the draft before Start, Finish or Discard runs and save it back afterwards. `core:domain` stays Koin-free (ADR-0008), so these wrappers, not the shared use cases directly, are what `LiveWorkoutViewModel` and Train home call. Measured cost: a worst-case 50-exercise × 50-set workout rewrites 2 550 rows per edit; fine for SQLite at this scale. A granular DAO is a follow-up only if manual testing shows lag.

### Prefill rules
Three pure functions in `core:domain` (`Prefill.kt`) share one rule: a new set is uncompleted, with no RPE, and its weight/reps come from the matching position of the exercise's **last performance** (its sets in the most recent finished workout containing it, first occurrence if it appears twice, computed by `FindLastPerformanceUseCase`) when one exists.
- `prefilledSetsForAddedExercise`: copies the last performance position by position; no history gives one empty Normal set.
- `prefilledSetsForTemplateExercise`: one Normal set per the template's `targetSets`; a position past the last performance's length falls back to a blank weight and reps at the bottom of the template's `targetReps` range (or blank with no range).
- `prefilledSetToAppend`: Add Set copies the last performance's set at the exercise's next position when one exists, else the exercise's own current last set, else blank.

Whether a value is still "prefilled" (and so shown muted) rather than a value the user touched is **not** stored on the entity: it is a `Set<WorkoutSetId>` the ViewModel keeps in memory only (`LocalState.touchedSetIds`, below), because adding a local-only Room column would touch `core:database`/`core:data`/the domain model for a cosmetic flag. A completed set is never shown muted even if untouched. Accepted consequence: a process death loses the distinction, and a prefilled-but-untouched value just reads as a normal one on restore.

### One active workout, started and finished through shared use cases
`StartEmptyWorkoutUseCase`/`StartWorkoutFromTemplateUseCase` (`core:domain`, shared with Train home, the template screens and the mini bar, all of which can start or finish a workout) both check `WorkoutRepository.observeActiveWorkout()` first and return `StartWorkoutError.WorkoutAlreadyActive(activeWorkoutId)` instead of creating a second one; the UI never needs to show that error because Train only ever offers Resume once one exists. `FinishActiveWorkoutUseCase` drops every uncompleted set, then every exercise left with no sets, stamps `finishedAt = now` and saves through the existing `SaveFinishedWorkoutUseCase` (validation + entity-and-outbox-in-one-transaction + PR recompute, unchanged). This is deliberately the whole "Finish" behaviour before REP-38 ships the confirmation dialog and the summary screen: no confirmation, immediate finish; REP-38's dialog calls `FinishLiveWorkoutUseCase` (the locked wrapper, see above), not `FinishActiveWorkoutUseCase` directly, so its confirmation sits in front of the same serialized write rather than bypassing the lock.

### In-memory UI state and the keypad target
Beyond `touchedSetIds`, `LiveWorkoutViewModel` keeps the editing field, reorder mode, the workout-name and exercise-notes drafts, and the single pending undo entirely in memory (`LocalState`, never a Room column): a newer delete (set or exercise) replaces whatever undo was already pending, and `Close` (minimize, discard, finish, or no active workout) drops it. The keypad's target (`LiveKeypadTargetUi`, including "same as last": the previous set of the same exercise in this workout, or the Previous-column set for the first one) is derived from `LocalState.editingField` and the latest workout snapshot on every recompute, never stored itself.

The name and notes drafts persist through `EditActiveWorkoutUseCase` 500 ms after the last keystroke (`DraftPersistDebounce`), each capped while typing — not just on save — at `ValidationLimits.NAME_MAX_LENGTH` (100 characters) for the name and `NOTES_MAX_LENGTH` (2 000 characters) for exercise notes. Minimize, Finish and `LiveWorkoutViewModel.onCleared()` all flush any in-flight debounced draft immediately instead of waiting for it: `onCleared` does so on an app-scoped `CoroutineScope`, since `viewModelScope` is already cancelled by the time it runs.

### Full-screen destinations
`LiveWorkoutRoute` and `ExercisePickerRoute` (`feature:workout:api`) carry no nav bar. `ExercisePickerRoute` is a `data class(replacingWorkoutExerciseId: String? = null)` (Replace mode's target, `null` for Add), so `app:shared` names full-screen destinations with a predicate rather than a `Set<NavKey>`: `internal fun NavKey?.isFullScreen(): Boolean = this == LiveWorkoutRoute || this is ExercisePickerRoute`. `AppShellScaffold` gained an `isNavigationBarVisible: Boolean = true` parameter that `SignedInAppShellScaffold` sets from `!navigator.visibleBackStack.lastOrNull().isFullScreen()`. `false` hides the whole bottom bar (nav bar and mini bar both), not just the nav bar, since a full-screen destination has no mini bar either.

### Multi-add and Replace (REP-37)
The exercise picker (C13) replaces the v0 "tap one, close" flow with multi-select Add and a Replace mode opened from the live card menu.

- **`AddExercisesToActiveWorkoutUseCase`** replaces `AddExerciseToActiveWorkoutUseCase`: it takes the picker's whole ordered selection (`List<ExerciseId>`, duplicates allowed) and appends all of them in **one** locked read-modify-write, each prefilled from `FindLastPerformanceUseCase` exactly as the single-exercise version did. The picker, not the use case, is responsible for keeping the selection at or under `EXERCISES_PER_WORKOUT_MAX`; the use case still defensively truncates to what's left, in case the read-modify-write raced a slower-landing edit.
- **`ReplaceExerciseInActiveWorkoutUseCase`** (new) swaps one card's exercise in place: the card keeps its position and gets a **new** `WorkoutExerciseId` (so its `LazyColumn` key and local UI state, e.g. a keypad target, start over), empty notes, and sets prefilled from the new exercise's own last performance — exactly as if it had just been freshly added. A card with at least one completed set is not replaced silently: the picker shows a destructive confirmation first ("Its `n` logged sets will be removed"), and only a confirmed Replace calls the use case. Both this and `AddExercisesToActiveWorkoutUseCase` take `ActiveWorkoutWriteLock` directly, the same way the single-exercise use case did.
- The pure edit this needs, `Workout.withExerciseReplaced(id, replacement)`, lives in `core:domain` next to the rest of `ActiveWorkoutEdits.kt`'s family; an unknown id is a no-op, like every other edit in that file.
- The picker's own reads (the exercise list, the active workout, and which exercises were recently used) are `ObserveExercisePickerUseCase`'s `combine` of `ExerciseRepository.observeExercises()`, `ExerciseUsageRepository.observeRecentlyUsedExercises(limit)` and `WorkoutRepository.observeActiveWorkout()`. The recently-used-exercises read is **not** a `WorkoutRepository` method: it is its own small interface, `ExerciseUsageRepository` (`core:domain`), implemented by `OfflineFirstExerciseUsageRepository` over its own `ExerciseUsageDao` (`core:database`, a join across the workout and exercise tables) — kept apart so neither `WorkoutRepository` nor its three implementers (`OfflineFirstWorkoutRepository`, `FakeWorkoutRepository`, `WorkoutDao`) cross Detekt's `TooManyFunctions` threshold for one more read only the picker needs.

## Consequences
- Every write to the active workout, from any screen or use case — edit, add exercise(s), replace an exercise, start, finish or discard — goes through `EditActiveWorkoutUseCase`, `AddExercisesToActiveWorkoutUseCase`, `ReplaceExerciseInActiveWorkoutUseCase`, `StartEmptyLiveWorkoutUseCase`, `StartLiveWorkoutFromTemplateUseCase`, `FinishLiveWorkoutUseCase` or `DiscardActiveWorkoutUseCase`, and therefore through `ActiveWorkoutWriteLock`; a future feature touching the active workout must do the same rather than calling `WorkoutRepository.saveActiveWorkout`/`discardActiveWorkout`, `StartEmptyWorkoutUseCase`/`StartWorkoutFromTemplateUseCase` or `FinishActiveWorkoutUseCase` directly.
- `StartEmptyWorkoutUseCase`, `StartWorkoutFromTemplateUseCase`, `FindLastPerformanceUseCase` and `FinishActiveWorkoutUseCase` live in `core:domain` and are provided by `app:shared`'s `DomainModule` (Koin-free `core:domain`, ADR-0008 reason 4), the same way the REP-27 use cases are, since Train home, the template screens and REP-39's mini bar all need them too.
- `LocalState`'s cosmetic fields reset on process death; this is accepted, not a bug, and is covered by the manual test plan rather than a schema change.
- A later feature that needs a true full-screen destination (no nav bar) extends `NavKey?.isFullScreen()` instead of inventing a second mechanism.
