# ADR-0026: Offline-first repositories, preferences and derived-record maintenance

- **Status:** Accepted (2026-11-06, REP-27)

## Context
REP-23/REP-24 built the domain value types and the pure `calculatePersonalRecords` function; REP-87 wired `RepzDatabase` into Koin and added `current_user`. This issue gives every feature a domain-only way to read and write the three synced aggregates (`Workout`, `WorkoutTemplate`, `Exercise`), the derived `PersonalRecord`s and the user's preferences, all offline first — finishing the write path ADR-0023 described (`entity + outbox` in one transaction, sync requested after commit) with the `core:domain`/`core:data` layer that actually calls it. `core:sync` (REP-26) is developed in parallel and binds the real platform schedulers afterwards; the Decision section below (DAO/module ownership and the personal-record recompute contract) is the exact, self-contained split between the two issues.

## Decision
- **One repository interface per aggregate, not a reader/writer split.** `WorkoutRepository`, `WorkoutTemplateRepository`, `ExerciseRepository`, `PersonalRecordRepository` and `UserPreferencesRepository` each get exactly one `core:data` implementation, `OfflineFirst<Name>` (`@Single`, auto-bound to the interface). ARCHITECTURE §3's SOLID table's `WorkoutReader`/`WorkoutWriter` example is reworded: no consumer needs only half of a repository yet, so splitting would only add ceremony. `WorkoutRepository` is the largest, at 12 methods (6 reads, plus save/delete/undo/confirm for both the active and the finished workout) — see the detekt decision below.
- **Two small ports in `core:domain`.** `SyncScheduler.requestSync()` is fire-and-forget and is called after every synced write's own transaction commits, never inside it, so the sync engine can never run before the row is visible. `TransactionRunner.inWriteTransaction { }` lets a use case run several repository calls as one local transaction without `core:domain` importing Room. `core:data` binds `RoomTransactionRunner` (wraps `RepzDatabase.withWriteTransaction`) and a temporary `NoOpSyncScheduler`; `core:sync` (REP-26) deletes `NoOpSyncScheduler` in the same change that binds `AndroidSyncScheduler`/`IosSyncScheduler` to `SyncScheduler`, because Konsist D5 (one owner per definition) fails if both exist at once.
- **Validation sits at the outbox gate.** `saveFinishedWorkout`, `saveTemplate` and `saveCustomExercise` validate with new `core:domain` validators (`AggregateValidation.kt`) before writing anything; an invalid payload must never enter the outbox, because the server would reject it permanently (`validation-error`, ADR-0020). The active (unfinished) workout is a draft and is never validated — this is "validated on save" from ADR-0022, not a change to it. New `ValidationError`s: `TooManyExercises`, `TooManySets`, `FinishedBeforeStarted`, `TargetSetsOutOfRange`, `TargetRepsOutOfRange`, `RestOutOfRange`, `SecondaryMusclesIncludePrimary`, `WeeklyWorkoutGoalOutOfRange`. Limits: ≤ 50 exercises per workout/template, ≤ 50 sets per exercise, 1–20 target sets, target reps 1–999, rest 0–3600 s in whole seconds — the last shared by templates and preferences through a promoted `ValidationLimits.validateRest`, since both need the identical rule.
- **A corrupt stored row is logged and skipped, never thrown.** A `core:data` mapping failure (an unknown vocabulary value, a catalog row missing attribution, an invalid RPE, a half-null target-reps pair) drops that one row from a list flow with a Kermit `e` log, or returns `null` from a single-item read, instead of throwing. One bad row must not blank a screen or crash a collector ("no exceptions across layers", AGENTS.md §4); the server and the app's own validated writes should make this impossible in practice, but the mapping stays defensive anyway. This is unlike REP-87's one-row `current_user` cache, which keeps its own `error(...)` behaviour unchanged.
- **Personal-record maintenance.** `RecalculatePersonalRecordsUseCase(exerciseIds)` and `RecalculateAllPersonalRecordsUseCase()` each run inside one `TransactionRunner.inWriteTransaction { }`, so a concurrent recompute (a local finish racing a sync pull) can't interleave its read and its write — SQLite has a single writer. Saving, deleting or undoing the deletion of a **finished** workout recomputes the union of its exercise ids from before and after the change (`SaveFinishedWorkoutUseCase`, `DeleteWorkoutUseCase`, `UndoWorkoutDeletionUseCase`), because `personal_records` is derived from the non-deleted finished history (ADR-0023) and a deleted workout must stop holding a record. **This recompute is deliberately not atomic with the workout's own write**: `requestSync()` already runs right after that write's transaction (the rule above), so a crash between the two steps can leave a record stale until that exercise's next recompute — acceptable, since the data is always fully rebuildable and never a source of truth.

  **`core:sync` (REP-26) must call the same two use cases under this exact contract:**
  1. After each **non-restore** pull page that applied workout changes, **after** that page's transaction commits: `RecalculatePersonalRecordsUseCase(ids)`, where `ids` is the stored (pre-overwrite) exercise ids of every workout the page touched, read before overwriting or tombstoning it, **union** the exercise ids present in the page's incoming payloads.
  2. After a push is answered `deleted: true` for a workout (tombstoned locally): `RecalculatePersonalRecordsUseCase(ids)`, where `ids` is that workout's stored exercise ids (read before tombstoning).
  3. During the **initial restore**: no per-page recompute. Exactly once, after the restore's last page: `RecalculateAllPersonalRecordsUseCase()`. REP-26 may run it before or after saving `initial_pull_completed_at`, since the recompute is idempotent; if the app dies before both complete, REP-26 re-runs the recompute on the next start while `initial_pull_completed_at != null` and its own "records recomputed" marker (if it adds one) is missing — the marker's existence and shape are REP-26's call.
  4. Neither use case is ever called **inside** a sync transaction — always after that transaction's own commit, for the same single-writer reason as the rule above.
- **Preferences live in a new, Koin-free `core:datastore`**, mirroring how `core:database` knows no domain types. `UserPreferencesDataSource` wraps one `DataStore<Preferences>` file (`repz.preferences_pb`) behind six raw keys; defaults and vocabulary-text ↔ domain-enum mapping live only in `core:data`'s `OfflineFirstUserPreferencesRepository`. `UserPreferences.DEFAULT` is `UnitSystem.KG`, `ThemeMode.SYSTEM`, dynamic colour off, 150 s rest, haptics on, goal 4 (board 13, ADR-0024).
  - **Units (hybrid):** the effective unit is the device's own preference if the user set one on this device, else the signed-in account's cached `current_user.unit_system`, else kg. `setUnitSystem` writes only the device preference, so it works offline and applies instantly; mirroring it to the server with `PATCH /me` is deferred to REP-45, the first UI that changes units. `logOut()` clears the device unit preference, because it belongs to the account — the next signed-in account falls back to its own server value.
  - **Default rest:** 150 s (2:30), accepted range 0–3600 s in whole seconds, the same ceiling as a template's `restSeconds`. The slider's 15 s UI steps are a REP-45 concern, not a storage rule.
  - **Weekly goal:** `weeklyWorkoutGoal: Int` (workouts per week), default 4, accepted range 1–7. The setter ships now with no settings UI; what counts as a week (locale, week start) is decided together with the Train/History UI, not here.
  - **Scope:** every preference except the unit is device-wide and survives logout and account switches.
  - **Deferred:** wiring theme, dynamic colour and haptics into `RepzTheme` is REP-45 — there is no settings UI yet to change a value, and the first-frame flash (the DataStore's first emission arrives after the first composition) needs the launch hand-off (ADR-0025) designed together with the toggles.
- **`DataModule` (`core:data`) now provides all 8 Room DAO accessors** — `workoutDao`, `templateDao`, `exerciseDao`, `personalRecordDao`, `outboxDao`, `syncMetaDao`, `syncRejectionDao`, next to the existing `currentUserDao` — including the three `core:sync` doesn't consume yet, so `core:sync` (REP-26) never needs to declare a DAO provider of its own (Konsist D5).
- **`app:shared` gains a `DomainModule`,** providing the five use cases above as `@Factory` (`core:domain` stays Koin-free, ADR-0008 reason 4), added to `RepzApp`'s module list; `app:shared` also gains the `core:datastore` dependency its `PlatformModule` actuals need for `UserPreferencesDataSource`.
- **Detekt's `TooManyFunctions` threshold is raised to 12** (`allowedFunctionsPerInterface`/`allowedFunctionsPerClass` in `config/detekt/detekt.yml`, up from the default of 11), the same kind of standing exception as `CyclomaticComplexMethod.ignoreSimpleWhenEntries` (ADR-0009). `WorkoutRepository` has 12 methods by design — one method per operation, not a reader/writer split — and both its `OfflineFirstWorkoutRepository` implementation and its `core:testing` fake implement every one of them, so all three need the same threshold (user decision, 2026-11-06).

## Consequences
- Every synced write is still `entity + outbox` in one transaction (ADR-0023); this issue adds the validated, PR-aware `core:domain`/`core:data` layer above it that every feature calls from now on.
- `core:sync` (REP-26) declares no `DataModule` DAO provider — all 8 already exist. It does add its own `@Module` (`@ComponentScan("com.repz.app.core.sync")`) to `RepzApp`'s module list, and it must delete `NoOpSyncScheduler` in the same change that binds the real platform schedulers (`AndroidSyncScheduler`/`IosSyncScheduler`) to `SyncScheduler` — Konsist D5 (one owner per definition) fails if both exist at once.
- A later issue that needs a feature-shaped query (history summaries, search, paging) adds it to the relevant repository; it never needs a new `DataModule` DAO provider, since all 8 already exist.
- ARCHITECTURE.md's former "which unit to show is a presentation concern (`User.unitSystem`)" line was out of date and is corrected: the unit shown is `UserPreferencesRepository`'s effective value, not a plain read of `User.unitSystem`.

## Amendment (REP-35, 2026-11-06): the weight-step preference

- **A seventh preference, `weightStepKg`/`weightStepLb`.** The number keypad's ± buttons (ADR-0028) step a set's weight by an amount the user can change, per unit: `WeightStep` (`core:domain`'s `preferences` package) is `KG_0_5`/`KG_1_25`/`KG_2_5`/`KG_5`/`LB_1`/`LB_2_5`/`LB_5`, each carrying its own `UnitSystem`. `WeightStep.optionsFor(unitSystem)` is what the keypad's Step chip cycles through; `WeightStep.defaultFor(unitSystem)` is `KG_2_5`/`LB_5` — the smallest common plate pair, 2 × 1.25 kg or 2 × 2.5 lb (user decision 2026-11-06, REP-35 plan U3 sub-question).
- **Scope and shape follow the existing preferences exactly**, not a new pattern: device-wide, survives `logOut()` (like default rest), stored as two raw DataStore keys (`weight_step_kg`, `weight_step_lb`, the enum's own `name` as text — unlike `UnitSystem`/`ThemeMode`'s hand-written vocabulary text, since nothing server-side needs to read this value). `UserPreferencesRepository.setWeightStep(step: WeightStep)` writes only the key of `step.unitSystem`, so changing the kg step never touches the stored lb step (and vice versa) — the interface now has 8 methods, still under the 12 this ADR's body raised the Detekt ceiling to.
- **An unknown or wrong-unit stored value falls back to the default**, the same "corrupt row is logged and skipped" rule this ADR already states for mapping failures: `core:data`'s `toWeightStepOrNull` matches the stored text against both the enum name *and* `unitSystem`, so a value stored under the wrong unit's key (which can't happen through `setWeightStep` itself, but could from a manual DataStore edit or a future bug) is also treated as unknown rather than silently applied to the wrong unit.
- **No settings UI ships with this preference**, same as `weeklyWorkoutGoal` above — REP-45 adds the Settings row; REP-35 adds only the keypad's own Step chip (ADR-0028, DESIGN_SYSTEM §9/§13) as an immediate way to change it.
