# ADR-0027: Client sync engine: handler registry, scheduling, status and Koin wiring

- **Status:** Accepted (2026-11-06, REP-26)

## Context

ADR-0026 (REP-27) finished the domain/`core:data` side of offline-first: validated writes, `TransactionRunner`, the two personal-record recompute use cases, and a temporary `NoOpSyncScheduler` because the real engine didn't exist yet. This issue (REP-26) builds that engine — one shared `SyncEngine` in `core:sync` `commonMain` that pushes the outbox and pulls pages, per-type `SyncHandler`s, `SyncStatus`/`RestoreState`, and the Android (`WorkManager`) and iOS (`BGTaskScheduler` + an in-process trigger) schedulers — and wires all of it into `app:shared`'s Koin graph, deleting `NoOpSyncScheduler` in the same change (Konsist D5: one owner per definition).

## Decision

- **Handlers are an explicit registry, not Koin multi-binding.** `SyncHandlerRegistry` (`@Single`) builds `WorkoutSyncHandler`/`TemplateSyncHandler`/`ExerciseSyncHandler` itself from the DAOs it is given; the three handlers are plain classes, not Koin definitions (they bind nothing, so Konsist D5 sees nothing). Adding a type means adding a handler class plus one line in the registry's list; `SyncEngine` never names an entity type. `getAll<SyncHandler>()` multi-binding was rejected: three classes auto-binding one interface would collide under D5, and `List<T>` constructor injection through the compiler plugin was unverified.
- **`core:sync` declares no DAO provider.** It injects the eight DAO bindings ADR-0026's `DataModule` already provides, plus `RepzDatabase` (bound in `PlatformModule` since REP-87) for `withWriteTransaction` around each push response and pull page. `TransactionRunner` stays a domain-use-case port; `core:sync` is not domain code, so it opens its own transactions directly.
- **A null `SyncHandler.buildUpsert` always drops the outbox row.** The interface returns one nullable `PushChangeDto?` for two reasons that can't be told apart from the return value alone — the row is missing, or (for a workout) it is still active. ARCHITECTURE §5.4 already makes both cases defensive-only: an active workout never actually reaches the outbox. `OutboxPusher` therefore always calls `outboxDao.deleteIfUnchanged(type, id, revision)` on a null result and logs at `warn`; the revision guard still protects a row a concurrent write re-enqueued between the read and the drop. A dropped row is harmless: a later legitimate write re-enqueues its own.
- **Personal-record refresh is a `core:sync`-owned port, adapted in `app:shared`.** `PersonalRecordsRefresher { refreshAll(); refreshForExercises(ids: Set<Uuid>) }` lives in `core:sync`, keeping the engine testable with a recording fake without depending on `core:domain`'s use cases. `PersonalRecordsRefresherAdapter` (`app:shared`, `@Single`) injects `RecalculatePersonalRecordsUseCase`/`RecalculateAllPersonalRecordsUseCase` and maps `Uuid` → `ExerciseId`, the one place that conversion happens. `refreshAll()` runs **before** `sync_meta.initial_pull_completed_at` is saved (the reverse of ADR-0026's handoff text), so a kill between the two leaves the flag unset and the next run's `hasMore == false` check re-runs `refreshAll()` — idempotent, since it replaces the whole table — needing no separate "records recomputed" mark.
- **A real Koin cycle surfaced once the adapter joined the graph, fixed with one `Lazy` edge.** Wiring `SyncModule` into `RepzApp` closed a genuine cycle the compiler plugin's `KOIN-D004` check caught: `PersonalRecordsRefresherAdapter` → a recompute use case → `WorkoutRepository` (`OfflineFirstWorkoutRepository`) → `SyncScheduler` → iOS's `PlatformModule.syncScheduler()` provider → `SyncEngine` → `PersonalRecordsRefresher` → `PersonalRecordsRefresherAdapter` again. The fix lives entirely on the iOS provider: `syncScheduler(engine: Lazy<SyncEngine>, …)` instead of a direct `SyncEngine` parameter, since `IosSyncScheduler` only calls `engine.value.sync()` from inside a triggered run, never at construction. Android's `AndroidSyncScheduler(context)` never took a `SyncEngine` dependency, so it never had this cycle. `PersonalRecordsRefresherAdapter` itself stays a plain, eagerly-constructed class — the cycle is broken on the one edge that actually needs it, not duplicated elsewhere.
- **`binds = [SyncScheduler::class, BackgroundSyncScheduler::class]` worked directly on both platform providers.** The plan's fallback (a separate `@Single fun syncScheduler(scheduler: BackgroundSyncScheduler): SyncScheduler` alias provider in `SyncModule`, if the compiler plugin rejected `binds` on a provider function) was never needed: `PlatformModule.syncScheduler()` on both Android and iOS binds its one instance to both interfaces directly, so `SyncCoordinator` (asking for `BackgroundSyncScheduler`) and everything else (the shell, the offline-first repositories, asking for `SyncScheduler`) share the same singleton. No ADR-0008 amendment needed.
- **Scheduling.** Android: `AndroidSyncScheduler` (`core:sync` `androidMain`) wraps `WorkManager`, resolved lazily so a host-JVM Koin graph test never initialises it. `requestSync()` → `enqueueUniqueWork("repz-sync", KEEP, NetworkType.CONNECTED, 30 s exponential backoff)`; `schedulePeriodic()` → `enqueueUniquePeriodicWork("repz-sync-periodic", KEEP, 1 h, CONNECTED)`; `cancelAll()` cancels both. `RepzApplication` implements `Configuration.Provider`, building `WorkManager`'s `Configuration` from a Koin-resolved `SyncWorkerFactory(syncEngine::sync)` (`repzWorkManagerConfiguration`, `app:shared` `androidMain`); the manifest removes the default `WorkManagerInitializer` (`tools:node="remove"`) so this is the only configuration used. No artificial write-debounce: outbox coalescing plus the engine's own final push pass (push again after the pull, in case a row became ready during it) covers writes made during a run; `ExistingWorkPolicy.KEEP` (not `APPEND_OR_REPLACE`) avoids growing chains.
- **iOS scheduling.** `IosSyncScheduler` drives everything from one `Channel.CONFLATED` request queue consumed by a single loop on `applicationScope`, each triggered run wrapped in a `UIApplication.beginBackgroundTask`/`endBackgroundTask` assertion so the app isn't suspended mid-run; a burst of `requestSync()` calls coalesces to at most one more run. `start()` registers the `BGTaskScheduler` launch handler (`com.repz.app.sync.refresh`, must happen before the app finishes launching) and starts an `NWPathMonitor`-backed connectivity watcher, whose unsatisfied→satisfied transition calls `requestSync()`. `schedulePeriodic()` submits a `BGAppRefreshTaskRequest` for +1 h, re-submitted at the start of every refresh run; the handler's `expirationHandler` cancels the run's job and `setTaskCompletedWithSuccess` reports `Completed`/`SkippedSignedOut` as success. `Info.plist` gets `BGTaskSchedulerPermittedIdentifiers = [com.repz.app.sync.refresh]` and `UIBackgroundModes = [fetch]`. `startRepzSync(koinApplication)` (`app:shared` `commonMain`) is called synchronously from `RepzIOSApp.init` right after `startRepzKoin`, never from `startRepzKoin` itself, so Koin graph tests stay side-effect free.
- **`BGTaskScheduler.submitTaskRequest` always fails on the iOS Simulator** (`.unavailable`): logged at `warn` and swallowed, never fatal, confirmed by Spotter's manual check that registration doesn't crash and the failure is logged. A real scheduled run is only checkable on a device; **REP-92** ("Manual device check: iOS BGAppRefreshTask sync", like REP-60) covers it as a follow-up, not a blocker for this issue.
- **The shared foreground/login trigger lives in `app:shared`'s `RepzAppShell`**, not per-platform `scenePhase`/`ProcessLifecycleOwner` code: a `LifecycleStartEffect(isSignedIn)` calls `koinInject<SyncScheduler>().requestSync()` whenever `isSignedIn == true`. Compose Multiplatform's iOS lifecycle maps `willEnterForeground` to `ON_START`, so one effect covers both platforms' foreground row, and `isSignedIn` flipping from `null`/`false` to `true` re-keys the effect, covering "just logged in" too. A debug-signed-in session (ADR-0025) still calls `requestSync()`, but `SyncEngine.sync()` re-checks the real session and returns `SkippedSignedOut` with zero requests, so the debug flag stays side-effect free on the wire.
- **No retry cap in v1.** A row that keeps failing (a whole-request 4xx, a single change still over the size cap after a 413 split) gets `incrementAttempts` and a `warn` log, then waits for the next run; each ready row is attempted at most once per run, so a run always terminates. REP-45's Sync details can surface a stuck row later.
- **`SyncStatus`/`RestoreState` stay two flows**, not one combined shape: `SyncMonitor { status: StateFlow<SyncStatus>; restoreState: Flow<RestoreState> }`, implemented by `SyncStatusTracker` (`@Single`). `status` combines run state, the outbox's pending count and `sync_meta`; `restoreState` is `InProgress(RestoreProgress?)` until `initial_pull_completed_at` is set, then `Completed`. Status mapping:

  | Run state | `status` |
  |---|---|
  | running | `Syncing` |
  | last outcome `RetryLater(null)` | `Offline(pendingCount)` |
  | last outcome `RetryLater(reason)` or `Failed(reason)` | `Error(reason)` |
  | otherwise | `Idle(lastSuccessfulSyncAt)` |

  Outcome mapping (`SyncErrorMapping`, `WorkResultMapping`):

  | `NetworkError` | `SyncOutcome` | Android `Result` |
  |---|---|---|
  | `Offline`, `Timeout` | `RetryLater(null)` | `retry()` |
  | `Api(5xx)` | `RetryLater(ServerUnavailable)` | `retry()` |
  | `SessionExpired` or `Api(401)` | `SkippedSignedOut` | `success()` |
  | `Api(other 4xx)` | `Failed(Unexpected)` | `failure()` |
  | `MalformedResponse` | `Failed(IncompatibleData)` | `failure()` |
  | — | `Completed`, `Stopped` | `success()` |

- **Logout (today, this issue).** `SyncCoordinator` collects `SessionRepository.sessionState`: `SignedIn` schedules the periodic work, `SignedOut` calls `scheduler.cancelAll()` and `engine.stop()` (a cooperative flag checked between transactional units of work — one push batch, one pull page — so a stopped run always leaves the database at a transaction boundary and returns `SyncOutcome.Stopped` rather than throwing; Konsist E1 bans a hand-written `catch (CancellationException)` that doesn't rethrow it). **Nothing is wiped.** User A's rows, outbox and `sync_meta` stay on the device; if user B then logs in on the same device, B's first sync pushes A's pending rows (rejected `id-conflict`, marked "couldn't sync") and pulls from A's cursor, missing B's older history. This is unchanged until **REP-45** ships the wipe-with-unsynced-warning flow (tracked there as blocked by this issue); multi-account use on one device is unsupported until then — acceptable, since only dev devices run this build today (ADR-0023). The engine also re-checks the session at the start of every run, so `SessionExpired` maps to `SkippedSignedOut` and nothing runs signed out.

## Consequences

- `core:sync`'s only Koin-visible surface is `SyncModule`'s scan (`SyncEngine`, `SyncHandlerRegistry`, `SyncStatusTracker`, `SyncCoordinator`) plus the two platform `PlatformModule` scheduler providers; `SyncScheduler` has exactly one owner per platform now that `NoOpSyncScheduler` is deleted.
- A future syncable entity (`sync-entity` skill) adds a handler class and one `SyncHandlerRegistry` line; it never touches `SyncEngine`, `core:sync`'s DI, or this ADR's Koin wiring.
- REP-31 (the Restoring screen) and REP-45 (sync indicator, "couldn't sync" marks, logout wipe) read `SyncMonitor` and build on this issue's status/restore shapes without changing them.
- REP-88's revoke retry can reuse this issue's trigger points (the WorkManager network constraint, `NWPathMonitor`) with its own job; it is not part of the engine, which requires a signed-in session.
