# ADR-0025: App shell and session-driven auth gate

- **Status:** Accepted (2026-11-03, REP-28)

## Context
`app:shared` needs one root that decides, before any feature screen renders, whether to show the signed-out auth flow (Welcome / Register / Login, `feature:auth:api`) or the signed-in four-tab shell (Train / History / Exercises / Profile, ADR-0017), and that keeps that decision in sync with the real session on every process start, sign-in and sign-out — without any screen reaching across that boundary itself, and without a tab losing its own navigation state when the user switches tabs.

## Decision
- **The session is the single source of truth.** `SessionRepository` (`core:domain`) exposes `sessionState: StateFlow<SessionState>` (`Unknown` / `SignedIn` / `SignedOut(reason)`) and `suspend fun restore()`. `OfflineFirstSessionRepository` (`core:data`, provided by `DataModule`) is the only implementation, wrapping `core:network`'s `SessionManager`. Screens never read or write the session themselves: login and register end in `SessionManager.start()` through their own feature's use case, logout in `SessionManager.end()`.
- **`AuthGate`** (`app:shared`'s `shell` package) is a plain, app-scoped Koin `@Single` — **not a `ViewModel`**. Konsist N1 scopes a `*ViewModel` class to a `feature:x:impl`'s `..presentation..` package with an `XUiState`/`XIntent`/`XEffect` sibling, and N4 allows `koinViewModel(` only inside a `*Screen`; `AuthGate` has neither shape and is read from `RepzAppShell`, not a screen. It is provided as `@Single fun authGate(...): AuthGate` in `AppModule` and read with `koinInject<AuthGate>()` + `collectAsStateWithLifecycle()`. No Konsist exemption was added for it.
  - `AuthGateUiState` is `Restoring` (the stored session hasn't been read yet; the shell shows only the plain brand background) or `Ready(isSignedIn: Boolean)`.
  - `AuthGate.state` maps `sessionState` and launches `sessionRepository.restore()` exactly once, in `init`, on the app-lifetime `CoroutineScope` (`CommonModule.applicationScope`) — once per process, never once per composition or per screen.
- **Reconciliation.** `RepzAppShell` derives `isSignedIn` from the gate (or `true` when the debug hook below is set) and runs `LaunchedEffect(isSignedIn) { isSignedIn?.let(navigator::syncAuthentication) }`. `Navigator.syncAuthentication(isSignedIn)` is a no-op when it already matches `Navigator.isAuthenticated`; otherwise the session wins and the navigator resets to the matching flow. This is what lets a `Navigator` restored from `rememberSaveable` (its own `isAuthenticated` flag, saved as part of `NavigatorState`) disagree with a session that changed while the process was dead — a refresh token that expired, for instance — and still end up correct: the restored flag is only the previous frame's guess, the session is the truth.
- **Brand-background guard.** While `isSignedIn == null` (still `Restoring`), or for the one frame before `syncAuthentication` catches the navigator up to a changed `isSignedIn`, the shell shows `BrandBackground` instead of `AppShellScaffold`, so the wrong stack — auth shown signed in, or the tab shell shown signed out — is never drawn, not even for a frame.
- **Navigator** (`core:navigation`) keeps one back stack per `TopLevelDestination` — Train (`feature:workout:api`'s `TrainRoute`), History, Exercises, Profile (`feature:settings:api`'s `ProfileRoute`) — plus one auth back stack (`feature:auth:api`'s `WelcomeRoute`/`RegisterRoute`/`LoginRoute`). `selectTopLevel` is a no-op while `!isAuthenticated`: the nav bar isn't shown signed out, but a stray call is still safe.
- **Visible entries and content keys.** `Navigator.visibleEntries: List<VisibleNavKey>` tags every key on the Train stack plus the selected tab's stack (or the auth stack alone, signed out) with the `BackStackId` that owns it (`Auth` or `Tab(destination)`) and its depth there. `VisibleNavKey.contentKey` (`"$stack/$depth/$key"`) disambiguates the same `NavKey` appearing twice in the visible list at once — Train's own root shown alongside the selected tab's root, or the same key pushed twice within one stack — so each still gets its own saveable state and `ViewModelStore`.
- **Per-stack decorators keep each tab's state alive while it is hidden.** Each of the five back stacks (the four tabs plus auth) keeps its own `rememberSaveableStateHolderNavEntryDecorator()` / `rememberViewModelStoreNavEntryDecorator()` pair, built once per stack with `rememberDecoratedNavEntries(backStack, entryDecorators, entryProvider)` and composed unconditionally — not only while that stack happens to be the one on screen. `RepzNavDisplay` passes `NavDisplay(entries: List<NavEntry<T>>, onBack = …)` only the concatenation of the stacks that are actually visible (Train + the selected tab, or auth alone). This matters because navigation3 disposes a decorator's saved state for an entry the moment that entry leaves the list the decorator is watching; a decorator that only ever sees the currently visible entries would drop a hidden tab's scroll position, text input and `ViewModel`s on every switch, which defeats the point of keeping a separate back stack per tab.
- **Every `feature:x:api` `NavKey` is a `@Serializable` `data class`/`data object`**, never a plain `class`/`object`: `VisibleNavKey.contentKey` depends on `NavKey.toString()` being stable across process death, which only a `data class`/`data object` guarantees.
- **Debug signed-in hook.** `RepzRoot(…, debugSignedIn: Boolean = false)` forwards into `RepzAppShell`, which then treats the session as signed in without any stored tokens, so the signed-in shell can be reached by hand before a real login flow exists. Android reads the `repz.debugSignedIn` intent extra only in debuggable builds (`MainActivity`); iOS reads the `-RepzDebugSignedIn YES` launch argument only under `#if DEBUG` (`ComposeView.swift`, forwarded to `mainViewController(…, debugSignedIn:)`). A release build never reads either and always passes `false`.
- **Placeholders.** `repzEntries()` (`app:shared`'s `RepzEntries.kt`) has one entry per root key today: `WelcomeRoute` renders `BrandBackground` (`// TODO(REP-30): replace with authEntries(navigator)`, which also re-adds a `navigator: Navigator` parameter to `repzEntries`); each tab root renders `TabRootPlaceholder(destination)` behind its own `// TODO(REP-xx):` (Train REP-32, History REP-40, Exercises REP-42, Profile REP-45). Each placeholder is replaced in place by the feature that owns that root, never duplicated elsewhere.
- **Accepted: the Paper → surface one-tone shift.** The shell paints the brand colours (`Paper #F5FAFB` light / `Ink` dark) while the session restores, then hands off to the themed screen (`surface #F4FAFD` light); the one visible tone change at that handoff is accepted rather than matching the two exactly. On the current Welcome placeholder, `BrandBackground` sits inside the scaffold's content padding, so the status-bar and home-indicator bands briefly show `surface` while the body still shows `Paper` — imperceptible today, and it goes away once REP-30 makes Welcome edge-to-edge.
- **The nav-bar selection indicator is unrelated to this ADR and unchanged by it:** it is already the M3 `NavigationBar` default, 64×32 dp, matching DESIGN_SYSTEM §9. REP-48 (MOT-02) adds only the stretch motion, icon FILL 0→1 and the label weight 500→700 — not a size change.

## Consequences
- A feature screen can never desync the shown flow from the real session: it only ever calls `SessionManager.start()`/`end()` through its own use case, and `AuthGate` plus `syncAuthentication` do the rest.
- Switching tabs keeps every tab's full navigation and `ViewModel` state; only Train and the selected tab are ever drawn, but all five stacks stay decorated and alive underneath.
- `AuthGate` being a plain `@Single` rather than a `ViewModel` means it has no `onCleared()`; it lives and is collected for the whole process, which is intended (there is exactly one, app-wide).
