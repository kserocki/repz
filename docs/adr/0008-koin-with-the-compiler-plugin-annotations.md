# ADR-0008: Koin with the compiler plugin (annotations)

- **Status:** Accepted (2026-10-28). Amended 2026-10-29 (REP-7): decision changed to explicit provider functions after the REP-7 spike found cross-module `@ComponentScan` broken on Kotlin/Native. Amended 2026-11-03 (REP-25): added the S1 pattern for a binding that needs a platform-only constructor argument (`Context`). Amended 2026-11-03 (REP-28): `@KoinViewModel` verified as a cross-module provider function on Android and iOS (the S1 spike), with the `api`-dependency rule that makes it work. Amended 2026-11-05 (REP-87): the S1 pattern's predicted REP-27 reuse for `RepzDatabase` happened in REP-87 instead (ADR-0023 amendment), landing first. Amended 2026-11-05 (REP-58): decision reverted to class-level definitions with one `@ComponentScan` per Gradle module, superseding the REP-7 amendment, now that koin-compiler-plugin 1.2.3 fixes the cross-module scanning bug the REP-7 amendment worked around.

## Context
We want DI errors at compile time instead of at runtime.

## Decision
Every Gradle module with definitions exposes **one** `@Module` class whose bindings are explicit `@Single`/`@Factory`/`@KoinViewModel` provider functions declared inside it — not self-annotated concrete classes discovered via `@ComponentScan`. `@KoinViewModel` works as a cross-module provider on Kotlin/Native (verified by REP-28's S1 spike, see its amendment below), as long as the module declaring the `ViewModel` subclass exposes the lifecycle `ViewModel` dependency as `api`. `app:shared` is the exception: its own module and its `@KoinApplication` entry point always compile together, so it may keep a local `@ComponentScan("com.repz.app.shared")`. One `@KoinApplication` entry in `app:shared` (`RepzApp`, started via `startRepzKoin()`), with its `modules` list built explicitly (no `@Configuration` auto-discovery).

`core:domain`'s and `core:common`'s own shared definitions stay out of those modules (both remain Koin-free): `app:shared` provides them instead, through a `DomainModule` (shared use cases) and a `CommonModule` (`Clock`, `IdGenerator`, dispatchers) — `CommonModule` landed with REP-23, `DomainModule` lands with REP-27. Features provide only their own feature-local use cases. Each definition has exactly one owner, since Koin resolves a duplicate binding last-wins at runtime and the compiler plugin isn't verified to flag that at compile time (Konsist rule D5 enforces one owner).

## Consequences
A broken graph doesn't compile, verified by `app:shared`'s per-platform main and test compile tasks, which cache normally. This also auto-enables `strictSafety`, which stops `app:shared`'s common-metadata compile task from ever reporting up-to-date, though that task itself runs no graph check. The plugin is young: Kotlin 2.4.21 is not on its verified list and warns on every Kotlin compile task, with source, in a module that applies `repz.koin` (35 tasks today) — confirmed in REP-7, never blocks.

REP-7's spike found a real bug: cross-module `@ComponentScan` hints are dropped by the Kotlin/Native KLIB serializer on Kotlin 2.4.20+ (koin-compiler-plugin#106 / KT-79565) — a binding scanned in one Gradle module is invisible to the plugin when a different module compiles against it. Reproduced with a binding that resolved correctly, both at compile time and at runtime, on the JVM/Android target, while the identical binding failed to compile (`[Koin][KOIN-D002] Missing definition`) on both `iosArm64` and `iosSimulatorArm64`. Fixed upstream by PR #129, unreleased as of plugin 1.2.1. Until 1.2.2 ships, every module pays the cost of writing one explicit provider function per binding instead of relying on scanning — more boilerplate, but it is what keeps compile-time safety across module boundaries today. Re-check cross-module `@ComponentScan` in REP-58.

## Amendment (REP-25, 2026-11-03): the S1 pattern for a Context-dependent binding

`core:network`'s `SecureStringStorage` is the first binding that needs a platform type (Android's `Context`) as a constructor argument. `app:shared`'s `commonMain` declares `@Module expect class PlatformModule` with no members; each platform's `actual class PlatformModule` adds its own `@Single fun secureStringStorage(...)`. `Context` is only ever a provider-function **parameter**, never an `actual class` constructor parameter — the Koin compiler plugin does not support generating code for a constructor parameter of an `expect`/`actual` class (koin-compiler-plugin#37). `RepzApp`'s `@KoinApplication(modules = [...])` list includes `PlatformModule::class` alongside `NetworkModule::class`.

Two same-named `actual class PlatformModule` definitions (one per platform source set) would otherwise look like two owners of the same binding to Konsist rule D5 (§12.2); D5 has a documented exception for this exact shape: a binding provided once per platform inside an `expect`/`actual` `@Module` counts as one owner when every `actual` shares the same fully qualified class name and sits in its own source set.

A compile-time graph test needs the same `Context` dependency the real app gets from `androidContext(...)`: `app:shared`'s `commonTest` declares `internal expect val platformTestDeclaration: KoinAppDeclaration`; its Android `actual` binds `single<Context> { Application() }` (a plain host `Application()`, not an Android instrumentation context); its iOS `actual` is a no-op, since `KeychainSecureStringStorage` takes no `Context`.

REP-27 (the Room database builder, which also needs `Context`) reuses this pattern rather than inventing a second one. (Correction, REP-87 amendment below: this binding was actually landed by REP-87, which needed it first; REP-27 never had to.)

## Amendment (REP-28, 2026-11-03): `@KoinViewModel` verified as a cross-module provider

S1 (a 30-minute spike, throwaway worktree) added `@KoinViewModel fun koinProbeViewModel(dependency: KoinProbeDependency): KoinProbeViewModel` to `core:testing`'s one `@Module`, and resolved `KoinProbeViewModel` from `app:shared`'s `commonTest` — a different Gradle module. First attempt (the lifecycle `ViewModel` dependency as `implementation` in `core:testing`) failed `testAndroidHostTest` with:

```
e: ... KoinMultiModuleGraphTest.kt:37:42 Cannot access 'androidx.lifecycle.ViewModel' which is a supertype of
'com.repz.app.core.testing.koin.KoinProbeViewModel'. Check your module classpath for missing or conflicting dependencies.
> Kotlin compiler: MISSING_DEPENDENCY_SUPERCLASS
```

Changing that one dependency to `api` fixed it: **BUILD SUCCESSFUL** on `testAndroidHostTest`, `iosSimulatorArm64Test` and `compileKotlinIosArm64`, all green, no other errors.

**The rule:** a module that declares a class extending `ViewModel` and provides it as a `@KoinViewModel fun`, when that class is resolved by name from a *different* Gradle module (`koinViewModel<X>()`/`get<X>()`/`inject<X>()` outside the declaring module), must depend on the lifecycle `ViewModel` artifact (`androidx-lifecycle-viewmodel-compose`) as **`api`**, not `implementation` — `implementation` doesn't expose the `ViewModel` supertype on the consumer's compile classpath. `koin-core-viewmodel` itself stays `implementation` (it is never referenced by type from outside the declaring module). An ordinary feature `XViewModel`, declared and consumed only inside its own `feature:x:impl`, is unaffected: `KmpFeatureImplConventionPlugin`'s existing `implementation` dependencies already compile that case and don't need to change.

The provider shape is now final (ARCHITECTURE §9): `@KoinViewModel fun xViewModel(...)` inside a module's one `@Module`, resolved with `koinViewModel<X>()` in `XScreen` (Compose) or `get<X>()`/`inject<X>()` in a graph/unit test. (Superseded by the REP-58 amendment below: `@KoinViewModel` is now a class-level annotation on the ViewModel itself, not a module function; the `api`-dependency rule and the resolution calls are unchanged.)

Also landed with REP-28: the first app-lifetime `CoroutineScope` binding (`CommonModule.applicationScope`, `app:shared`); `core:data`'s own `DataModule` (its first binding, `SessionRepository`); and `KmpFeatureImplConventionPlugin`'s `commonMain` now carries the viewmodel (`koin-core-viewmodel`, `koin-compose-viewmodel`), lifecycle (`androidx-lifecycle-viewmodel-compose`, `androidx-lifecycle-runtime-compose`) and immutable-collections (`kotlinx-collections-immutable`) dependencies every `feature:x:impl` needs, resolving the `TODO(REP-28)` that REP-7 left in that plugin.

**Benign warning, not a build failure:** `koin-core-viewmodel:4.2.2` transitively pulls lifecycle `2.9.6` against the project's pinned `2.11.0`, which prints `KLIB loader: the same 'unique_name=...' found in more than one library` during an `iosMain`/`iosTest` metadata compile of any module applying `repz.kmp.feature.impl`. The real per-platform compile (e.g. `compileKotlinIosSimulatorArm64`) is unaffected and warning-free; no action was taken.

## Amendment (REP-58, 2026-11-05): class-level definitions supersede explicit providers

**Evidence**, a 3-step experiment on `AuthModule`/`LoginViewModel`/`RegisterViewModel` (`app:shared`'s `AuthGraphTest`, `testAndroidHostTest` + `iosSimulatorArm64Test` + `compileKotlinIosArm64`):

1. Class-level `@KoinViewModel` alone, no `@ComponentScan` on `AuthModule`: `[Koin][KOIN-D002] Missing definition: LoginViewModel`/`RegisterViewModel` on **both** platforms — an annotated class nobody scans is never registered, on any target.
2. Add `@ComponentScan("com.repz.app.feature.auth.impl.presentation")` to `AuthModule`, koin-compiler-plugin **1.2.1**: Android host green; iOS still `KOIN-D002` — the REP-7 bug (cross-module `@ComponentScan` hints dropped by the Kotlin/Native KLIB serializer, koin-compiler-plugin#106 / KT-79565).
3. Same scan, plugin **1.2.3**: `AuthGraphTest` 4/4 green on `testAndroidHostTest` **and** `iosSimulatorArm64Test`; `compileKotlinIosArm64` green.

#106 is fixed upstream in 1.2.3 (PR #129): a definition scanned in one Gradle module is now visible to the plugin's compile-time safety check from a different module, on Kotlin/Native as well as the JVM/Android target.

**Decision, superseding the REP-7 amendment above:** every Gradle module with definitions exposes one `@Module` class with exactly one `@ComponentScan("<module root package>")`, and every project class that can carry a Koin annotation does: `@Single` (repositories, API services, stores, app-scoped holders), `@Factory` (feature use cases), `@KoinViewModel` (ViewModels). This is what the original 2026-10-28 decision already wanted; the REP-7 amendment's explicit-provider-function workaround and its "no cross-module `@ComponentScan`" rule are **superseded**, along with ARCHITECTURE §9's "rule for readability" bullet that generalised it to every binding.

**Auto-binding.** Without `binds`, a class registers under its own type plus its direct supertypes that are interfaces or abstract classes, excluding `Any`, `KoinComponent`, `KoinScopeComponent`, `ViewModel`, `AndroidViewModel` (`detectAutoBindings`, verified against the 1.2.3 sources). It is not transitive: an interface reached only through an abstract base is not bound. `binds = [A::class]` binds exactly that list; `binds = []` disables auto-binding. Every repository, API service and store converted here has exactly one interface, so plain auto-binding is enough; `KoinMultiModuleGraphTest`'s `givenScannedClassInAnotherModule_whenResolvedByItsInterface_thenAutoBindingCrossesTheModuleBoundary` proves it crosses a Gradle module boundary on both platforms (`core:testing`'s `KoinProbeDependency` resolved by its `KoinProbeContract` interface from `app:shared`'s `commonTest`).

**What stays:** one owner per definition (Konsist D5, now aware of auto-bound interfaces, see below); the S1 pattern for `Context`-dependent bindings (`PlatformModule`); the REP-28 `api`-dependency rule for a `@KoinViewModel` class read from a Gradle module other than the one declaring it; the explicit `modules` list on `RepzApp` (no `@Configuration` auto-discovery); `app:shared` as the one `@KoinApplication` entry point.

**What an explicit provider function is still for**, each with a one-line KDoc reason naming it: (1) third-party types or values built by a function — `ApiConfig`, `RepzHttpClients` (`NetworkModule`); (2) Room-generated accessors — `DataModule.currentUserDao`; (3) platform-built types — `PlatformModule`'s S1 providers; (4) classes declared in `core:domain`/`core:common`, which stay Koin-free — `CommonModule`'s `clock()`, `idGenerator()`, `appDispatchers()`, `applicationScope()`; a future `DomainModule` will provide shared `core:domain` use cases the same way (REP-27); (5) qualified bindings (`@Named`), when they appear. `core:domain` and `core:common` see no Koin import or plugin either way (Konsist A1). Konsist D6 only rejects the pure pass-through shape (one uncomputed constructor call of a project class); that every remaining provider fits one of these five reasons is enforced in review.

**Defaults instead of providers.** A dependency that only needs a sensible default, such as a tagged Kermit `Logger`, is a constructor parameter with a default value (`logger: Logger = Logger.withTag(...)`). The compiler plugin's default `skipDefaultValues = true` doesn't inject a non-null, unqualified parameter that has a default, so `SessionManager` and `OfflineFirstAuthRepository` stay plain class-level `@Single`s instead of needing a provider function just for the tag. Tests pass their own logger explicitly.

`repz.koin` now also sets `koinCompiler { hiddenDependencyCheck = "error" }` (new in the compiler plugin, opt-in): it fails the build on a definition reachable only transitively, where compile-time safety can't see it. It did not fire on the current graph.

**Negative proof** (throwaway worktree, `core:testing`'s `KoinProbeDependency`/`KoinProbeContract`, every edit reverted, never committed):
- **N1**, `@Single` removed from `KoinProbeDependency`: `compileAndroidHostTest` fails with `[Koin][KOIN-D001] Missing dependency: KoinProbeDependency` (and `KoinProbeContract`); both iOS test compiles fail with `[Koin][KOIN-D002] Missing definition: KoinProbeDependency` / `KoinProbeContract`.
- **N2**, an unbound constructor parameter added to the still-scanned, still-annotated class: all three compiles fail with `[Koin][KOIN-D001] Missing dependency: KoinProbeUnboundDependency`.
- **N3**, a second provider function added for the same type **alongside** the still-scanned, still-annotated class — a duplicate definition: **the compiler does not catch it.** `BUILD SUCCESSFUL` on all three. The koin-compiler-plugin's compile-time safety checks reachability, not uniqueness; a duplicate resolves last-wins at runtime, undetected. **Konsist D5, not the compiler, is what enforces one owner per definition** — this is the measured confirmation of what the original decision and D5 already assumed.
- **N4**, `LogInUseCase` moved outside `AuthModule`'s scan package: `compileAndroidMain` and both iOS main compiles fail with `[Koin][KOIN-D001] Missing dependency: LogInUseCase` — stronger than expected, since it fails the real app's build, not just a test graph.

**Konsist D1–D7** (`:konsist-tests`, `KoinRules.kt`; full wording in ARCHITECTURE §12.2): D1 (one scan per module, non-overlapping), D2 (an annotated class must lie inside its own module's scan) and D5 (one owner, now keyed by auto-bound types too) were rewritten for class-level definitions everywhere, not only in `app:shared`; D3 and D4 are unchanged; D6 (no pass-through provider — annotate the class instead) and D7 (a class's name states its role, and the annotation kind must match: `*UseCase` → `@Factory`, `*ViewModel` → `@KoinViewModel`, `OfflineFirst*Repository` → `@Single`) are new. Each has a positive test against the real project and a negative fixture.

**Side effect (REP-61):** re-running REP-61's 3-build configuration-cache check (cold build, unchanged rebuild, rebuild after touching an unrelated `commonMain` file) on koin-compiler-plugin 1.2.3 reused the configuration cache every time — the "thrown away on every Kotlin edit" miss is confirmed fixed.
